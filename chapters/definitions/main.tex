\chapter{Formal foundations and datasets}
\label{chapter:definitions}
\input{abstract}

This chapter formalizes, in precise mathematical terms, the page, web article, template, and print article entities that \melody already manipulates natively as a feature of its production system (\secref{sec:basic-elements}). This formalization underlies every contribution developed in the remainder of this thesis.

\section{Core concepts and representations}
\subsection{Newspaper page ($\page$)}.
\label{sec:page-definition}

A page $\page$ (\figref{fig:page}) defines the empty canvas and its physical boundaries. Formally, $\page$ is represented as a tuple containing the structural dimensions:
\begin{equation}
\page = \langle \Wpage, \Hpage, \mtop, \mbottom, \mleft, \mright, \colsize, \gutter \rangle,
\label{eq:page-definition}
\end{equation}
where:
\begin{itemize}
    \item $\Wpage \in \mathbb{R}^+$ and $\Hpage \in \mathbb{R}^+$ denote the  width and height of the page, respectively, measured in millimeters (mm).
    \item $\mtop, \mbottom, \mleft, \mright \in \mathbb{R}^+$ represent the  margins that restrict the usable layout space from the outer boundaries of the page.
    \item $\colsize \in \mathbb{R}^+$ represents the fixed width of each column in the page layout. 
    \item $\gutter \in \mathbb{R}^+$ denotes the spacing between columns. 
\end{itemize}
Consequently, the effective width (\Weff) and height (\Heff) of the page canvas are defined as $\Weff = \Wpage - \mleft - \mright$ and $\Heff = \Hpage - \mtop - \mbottom$.

    \caption{Page $\page$}
    \label{fig:page}
\end{figure}

\subsection{Web article ($\articleobj{i}$)}
\label{sec:web-article}

A web article $\articleobj{i} \in \articleset$ (\figref{fig:article}), where  $\articleset$ is a set of articles, is defined the following tuple:
\begin{equation}
\articleobj{i} = \langle \Cart{i}, \Nimg{i}, \Tlart{i}, \Stlart{i}, \Mainart{i} \rangle,
\end{equation}
where:
\begin{itemize}
    \item $\Cart{i} \in \mathbb{Z}^+$ represents the total character count of the body text,
    \item $\Nimg{i} \in \mathbb{Z}_{\ge 0}$ denotes the number of images that \articleobj{i}\ contains,
    \item $\Tlart{i} \in \{0, 1\}$ is a binary flag indicating the presence ($1$) or absence ($0$) of a headline or title element,
    \item $\Stlart{i} \in \{0, 1\}$ is a binary flag indicating the presence ($1$) or absence ($0$) of an accompanying subtitle,
    \item $\Mainart{i} \in \{0, 1\}$ is a binary flag indicating whether the article is designated as the main lead story ($1$) within the page context. Only one article per page can be indicated as main.
\end{itemize}
\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\widthForOneImage]{img/article-with-notation.pdf}
    \caption{Web article $\articleobj{i}$}
    \label{fig:article}
\end{figure}

\subsection{Template ($\templateobj{j}$)}
\label{sec:template}
Formally, an article template $\templateobj{j} \in \templatecatalog$ (\figref{fig:template}), where $\templatecatalog$ is a set of templates, is characterized as follows:

\begin{equation}
\templateobj{j} = \langle \Wtemp{j}, \Htemp{j}, \zoning{j}, \capacity{j} \rangle,
\end{equation}

where:
\begin{itemize}
    \item $\Wtemp{j} \in \mathbb{R}^+$ and $\Htemp{j} \in \mathbb{R}^+$ represent the  width and height of the template layout, respectively, measured in millimeters (mm). In the case of the page generation task (Chapter~\ref{chapter:pagegen}), $\Wtemp{j}$ strictly adheres to the horizontal column size $\colsize$ and gutter $\gutter$ defined by the page $\page$.
    \item $\zoning{j} = \{\zblock{j}{1}, \zblock{j}{2}, \dots, \zblock{j}{|\zoning{j}|}\}$ represents the zoning topology of the template, defined as a finite set of $|\zoning{j}|$ internal blocks. 
    Each block $\zblock{j}{k}$ is formalized as a pair
    $$\zblock{j}{k}= \langle \blockgeom{\zblock{j}{k}}, \blockfeat{\zblock{j}{k}} \rangle,$$
    where:
    \begin{itemize}
        \item $\blockgeom{\zblock{j}{k}}$ is an ordered set of cartesian coordinates (relative to $\templateobj{j}$ dimensions) that define the polygonal geometry of the block within the template layout.
        \item $\blockfeat{\zblock{j}{k}} \in \{\text{THEME}, \text{TITLE}, \text{SUBTITLE}, \text{PHOTO}, \text{CAPTION}, \text{TEXT}\}$ indicates the feature class assigned to the block.
    \end{itemize}
    Note that the image slots available (\Nimgmax{j}) is an implicit property derived from the zoning topology, such that $\Nimgmax{j} = |\{\zblock{j}{k} \in \zoning{j} : \blockfeat{\zblock{j}{k}} = \text{PHOTO}\}|$.

    \item $\capacity{j} \in (\mathbb{Z}^+)^{(\Nimgmax{j} + 1) \times 2}$\ is a text capacity matrix, which defines the body text capacity depending on the number of image slots kept for the print article. Note that this gives a single template the flexibility to accommodate a range of body text sizes by omitting some of its image slots. \melody adopted this design specifically to limit the size of the template catalog, since a single template can thereby serve several distinct configurations rather than requiring a dedicated template for each one.
    
    Formally, the text capacity matrix is defined by:
    \begin{equation}
        \capacity{j} =
        \begin{bmatrix}
        \capacity{j}[0, 0] & \capacity{j}[0, 1] \\
        \capacity{j}[1, 0] & \capacity{j}[1, 1] \\
        \vdots & \vdots \\
        \capacity{j}[\Nimgmax{j}, 0] & \capacity{j}[\Nimgmax{j}, 1]
        \end{bmatrix}
        \begin{array}{l}
        \leftarrow \text{0 active images} \\
        \leftarrow \text{1 active image} \\
        \\
        \leftarrow \Nimgmax{j} \text{ active images}
        \end{array}
    \end{equation}
where the elements in the $k$-th row denote the text capacity bounds when $k$ image slots are active, i.e., $k \leq \Nimgmax{j}$ image slots  are used to allocate an image. Specifically: %todo: add index active image 
\begin{itemize}
    \item $ \capacity{j}[k, 0]$ establishes the minimum character requirement,
    \item $ \capacity{j}[k, 1]$ defines the maximum character capacity.
\end{itemize}
These bounds are strictly determined by the area variations that occur when removing the $\Nimgmax{j} - k$ unused image slots from the template. Because the available image slots within a template may vary in physical dimensions (e.g., a large main photograph versus smaller secondary images), omitting different combinations of slots yields varying amounts of reclaimed space for the text block. Consequently, the minimum capacity $\capacity{j}[k, 0]$ is computed by assuming the omission of the smallest available photo slots (resulting in the least amount of expanded text area), whereas the maximum capacity $\capacity{j}[k, 1]$ is computed by omitting the largest available photo slots (yielding the maximum possible text area).

Note that the proposed formulation only assesses template suitability rather than determining which specific images to discard, leaving that selection decision to the human designer or external editorial software.
\end{itemize}

    \label{fig:template}
\end{figure}


\subsection{Print article}
When an article $\articleobj{i}$ is formatted to be placed in the page canvas, it means that an individual template $\templateobj{j} \in \templatecatalog$ has been assigned to $\articleobj{i}$, becoming a print article (\figref{fig:print-article}).

To formalize this, \templatesel{i} denotes the index of the selected template $\templateobj{\templatesel{i}} \in \templatecatalog$ for article $\articleobj{i}$. Formally,
\begin{equation}
\templatesel{i} \in \{1, 2, \dots, \catalogsize\}, \forall i \in \{1, 2, \dots, \numarticles\}.
\label{eq:template-selection-def}
\end{equation}

Note that after this selection, the article acquires the physical dimensions and characteristics of the assigned template. 
Additionally, the number of images $\Nimg{i}$ in the article fixes the number of active image slots in the template, which in turn determines the text capacity range $[\capacity{\templatesel{i}}[\Nimg{i}, 0], \capacity{\templatesel{i}}[\Nimg{i}, 0]]$ to respect in the optimization process.

\end{figure}

\subsection{Full page layout $\solution$}
\label{sec:solution}

A solution $\solution$ corresponds to the desired output of the web-to-print workflow. It is defined as a fully composed page layout in which every article $\articleobj{i} \in \articleset$ is assigned a template $\templateobj{\templatesel{i}}$ and is positioned within the physical boundaries of the page $\page$ (\figref{fig:solution}).

\section{Industrial Datasets}



To instantiate the formal definitions introduced in this chapter, empirical evaluations throughout this thesis rely on two industrial repositories provided by press publishers operating under the \melody content management system: \publihebdos~\cite{publihebdos} and \laprovence~\cite{laprovence}. Both repositories originate from the same underlying platform and therefore share a common data model for templates, but differ in scope: the \publihebdos repository exposes a template catalog together with its historical usage log, whereas the \laprovence repository exposes a template catalog together with a corpus of fully assembled historical page layouts. \laprovence could, in principle, also yield a usage log by aggregating template occurrences across its page corpus; however, since this repository was not employed for the template retrieval task addressed in Chapter~\ref{chapter:template}, such a derived log was not of interest and was not extracted. 

The remainder of this section describes the raw structure of both repositories (\secref{sec:publihebdos}, \secref{sec:laprovence}), and the preprocessing pipeline applied to derive the quantities required by the definitions of this chapter (\secref{sec:dataset-preprocessing}).


\subsection{\publihebdos archive}
\label{sec:publihebdos}

\subsubsection{Set of templates}

\publihebdos archive exposes its catalog of $\catalogsize = 452$ article templates $\templatecatalog$ through a collection of XML files, one per template. Each XML file specifies:
\begin{itemize}
    \item a unique identifier for the template;
    \item its width $\Wtemp{j}$ and height $\Htemp{j}$, together with the number of page columns it spans, which is redundant with $\Wtemp{j}$, since it strictly adheres to the column grid $\colsize$ and gutter $\gutter$ of the page $\page$ (\secref{sec:template});
    \item its number of image slots $\Nimgmax{j}$;
    \item the number of body text characters it can accommodate when all $\Nimgmax{j}$ image slots are occupied. This is a single raw quantity that, once combined with the preprocessing step described in \secref{sec:dataset-preprocessing}, yields the full text capacity matrix $\capacity{j}$ introduced in \secref{sec:template};
    \item its zoning $\zoning{j}$, given as the list of internal blocks $\zblock{j}{k}$, each one annotated with a semantic class $\blockfeat{\zblock{j}{k}}$ and a bounding box expressed relative to the template dimensions.
\end{itemize}
At this raw stage, the bounding boxes are allowed to overlap: in practice, the body text block is defined as a single large rectangle spanning the background of the template, while the remaining blocks (title, subtitle, images, captions) are layered on top of it. \secref{sec:dataset-preprocessing} describes how these overlapping boxes are later resolved into the non-overlapping polygonal geometry required by \secref{sec:template}. Each XML file is accompanied by a JPEG rendering of the template, in which every block is displayed with a placeholder graphic (\figref{fig:publihebdos-template-example}).

\subsubsection{Usage log}

In addition to the template catalog, \publihebdos provides a CSV usage log covering the six months preceding the data extraction, reporting for each template its identifier, its overall usage count $\templateutilization{j}$, and its per-month usage count. \figref{fig:publihebdos-usage-longtail} plots the resulting overall usage distribution across the catalog, reordered by decreasing usage: it exhibits a pronounced long-tail shape, with a small subset of templates (empirically, the top 4\% of the catalog, corresponding to a usage $\templateutilization{j}$ above $8000$) concentrating most of the recorded usage, while the majority of templates are used sparingly or not at all. This empirically observed threshold of $8000$ is reused in Chapter~\ref{chapter:template} to separate the short head from the long tail when evaluating template retrieval methods. More generally, this long-tail distribution motivates the design of the template retrieval mechanisms introduced in Chapter~\ref{chapter:template}, which account for popularity bias and long-tail exposure together with structural diversity.

\subsection{\laprovence archive}
\label{sec:laprovence}

\subsubsection{Set of templates}

\laprovence archive exposes its own catalog of $\catalogsize = 345$ article templates $\templatecatalog$, following the same XML and JPEG format described for \publihebdos in \secref{sec:publihebdos}.

%\subsubsection{Statistics}

\subsubsection{Set of pages}

In addition to its template catalog, the \laprovence archive provides a corpus of $6{,}007$ historical page layouts, each corresponding to a front or internal page of the daily newspaper composed by human operators within \melody. Each page is described by an XML file specifying:
\begin{itemize}
    \item a unique identifier for the page;
    \item its width $\Wpage$ and height $\Hpage$, its margins $\mtop, \mbottom, \mleft, \mright$, and its column grid $\colsize$ and gutter $\gutter$;
    \item for each article placed on the page:
    \begin{itemize}
        \item a unique identifier;
        \item its position and size ($x$, $y$, width, and height), expressed relative to the absolute page boundaries, i.e., ignoring the margins;
        \item the identifier $\templatesel{i}$ of the template selected for the article;
        \item a deep copy of the corresponding template's own XML file.
    \end{itemize}
\end{itemize}
Advertisements are not always represented in this XML format, since they are typically hardcoded directly onto the page rather than modeled as articles. 
Because $\Wtemp{j}$ strictly adheres to the column grid $\colsize$ and gutter $\gutter$ of the page $\page$ (\secref{sec:template}), an article's width always matches the width of its selected template exactly.
In contrast, its height may not, a discrepancy formally captured by the elasticity variable introduced in \secref{sec:decision-variables}. Similarly, an article may occupy fewer image slots than the $\Nimgmax{\templatesel{i}}$ available in the assigned template, though never more.

In practice, the page width $\Wpage$, height $\Hpage$, margins $\mtop, \mbottom, \mleft, \mright$, column size $\colsize$, and gutter $\gutter$ are fixed across the entire \laprovence page corpus:
\begin{itemize}
    \item $\Wpage = 289.0$ mm, $\Hpage = 360.0$ mm;
    \item $\mtop = 30.675$ mm, $\mbottom = 15.0$ mm, $\mleft = 15.0$ mm, $\mright = 15.0$ mm;
    \item $\colsize = 40.0$ mm, $\gutter = 4.0$ mm (e.g., a two-column span therefore measures $2\colsize + \gutter = 84.0$ mm).
\end{itemize}

A PDF rendering of the composed page is additionally provided alongside each XML file (\figref{fig:laprovence-page-example}).

\subsection{Preprocessing}
\label{sec:dataset-preprocessing}

\subsubsection{Template preprocessing}

As noted in \secref{sec:publihebdos}, the raw bounding boxes provided in the template XML files do not represent the actual topology of the internal blocks. Since several blocks (specially the body text block, defined as a single rectangle spanning the background) overlap with adjacent blocks, this raw geometry cannot be used directly to compute layout similarity between templates (\secref{section:modelling-similarity}). Consequently, each template is cleaned by computing intersection and union operations between the declared bounding boxes, using the CGAL library, to recover the actual polygon $\blockgeom{\zblock{j}{k}}$ that bounds each block.

Once the zoning $\zoning{j}$ has been cleaned in this way, the text capacity matrix $\capacity{j}$ is computed for each template following the definition given in \secref{sec:template}. The resulting template $\templateobj{j} = \langle \Wtemp{j}, \Htemp{j}, \zoning{j}, \capacity{j} \rangle$ is serialized to a JSON file, and a new PNG rendering is generated to visualize the cleaned zoning topology (\figref{fig:template-cleaned-topology}).

\subsubsection{Page preprocessing}

Before use, the \laprovence page corpus described in \secref{sec:laprovence} is filtered in two steps. First, all front pages are discarded, a requirement imposed by \melody, since front pages follow different, more free-form layout construction principles. Second, among the remaining pages, pages exhibiting spatial overflow or overlap between articles (indicating an exporting error) and pages referencing a template identifier absent from the corresponding template catalog (indicating a desynchronization between the two datasets) are also discarded. After these two filtering steps, $4{,}449$ pages remain usable.

These usable pages are then classified into four disjoint categories, based on the percentage difference, for each article on the page, between its actual height and the nominal height of its assigned template. 
\begin{itemize}
    \item pages composed of a single article spanning the full page, for which this height comparison does not apply: $953$ pages;
    \item pages with two articles or more, where every article's height matches its template's height exactly (a $0\%$ difference): $2{,}665$ pages;
    \item pages with two articles or more, where at least one article's height difference is non-zero but remains within the $[-15\%, 15\%]$ range -- i.e., the article may be either compressed or expanded relative to its template, within this admissible margin: $110$ pages;
    \item pages with two articles or more, where at least one article's height difference falls outside the $[-15\%, 15\%]$ range: $721$ pages.
\end{itemize}
The thresholds used for this classification ($[-15\%, 15\%]$) are not derived for this thesis. Instead, they are established by \melody itself as part of its own production guidelines. This percentage difference is later formalized, for the page generation task, as the elasticity variable introduced in \secref{sec:decision-variables}.

All $4{,}449$ usable pages are used to train the neural models described in Chapter~\ref{chapter:template} (\secref{sec:gwes}), which relies on the train/validation/test split described there; restricting training to a subset of these categories was deliberately avoided, since maximizing the amount of available data is preferable for training a neural model.

In contrast, only the exact-match and admissible-elasticity categories (amounting to $2{,}775$ pages) constitute the eligible pool for the evolutionary page generation algorithm of Chapter~\ref{chapter:pagegen}, since these are the only categories that remain representative of the range that formulation is designed to model. The procedure used to select the actual benchmark instances from this pool is described in \secref{subsec:dataset_characterization}.
